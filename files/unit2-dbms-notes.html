1. Objectives of the Database Approach

Before databases existed, organisations stored data in separate files for every application — a "payroll file" for the payroll program, a "student file" for the admissions program, and so on. This is called the file-based (traditional) approach. The database approach was developed to fix the problems this caused.

Fig 1: File-based approach (data duplicated per application) vs Database approach (one shared, centrally-managed store)

The database approach was introduced to achieve the following objectives:

1.1 Minimise Data Redundancy

In file systems, the same data (e.g. a customer's name and address) may be stored separately in the sales file, the billing file, and the shipping file. The database approach stores it once and lets every application access that single copy.

Example: In a college, "Student Name" and "Roll No." need not be stored separately in the Fees file, the Library file, and the Exam file — one central Student table is shared by all three modules.

1.2 Avoid Data Inconsistency

When the same fact is stored in several places, updating it in one place but forgetting another creates inconsistency — two files disagree about the same real-world fact. Centralising data removes this risk because there is only one value to update.

1.3 Data Sharing

Multiple users and multiple application programs can access the same database at the same time (with proper concurrency control), instead of each department keeping its own private, disconnected file.

1.4 Enforce Standards and Data Security

A DBMS lets the organisation define standards (naming, format, validation rules) centrally, and restrict who can view or edit which data through access control / permissions — something very hard to enforce consistently across many separate files.

1.5 Maintain Data Integrity

Integrity constraints (e.g. "Age cannot be negative", "Roll No. must be unique") are defined once in the database and automatically enforced for every application, rather than each programmer having to re-code the same checks.

1.6 Balance Conflicting Requirements

Different user groups may want the same data organised differently (e.g. Finance wants data sorted by cost centre, HR wants it by department). A DBMS, through its "views," lets each group see the data the way it needs, while physically storing it only once.

1.7 Data Independence

Applications are insulated from exactly how data is physically stored, so the storage structure can change without rewriting every application program (explained further in Section 6 — Three-level architecture).

In short: Objectives of the database approach = Reduce redundancy → Avoid inconsistency → Enable sharing → Enforce standards & security → Maintain integrity → Balance user needs → Give data independence.

2. Characteristics of Database Management Systems

A DBMS is software that sits between the physical database and the users/application programs, and lets you create, store, modify, retrieve, and manage data in a structured, controlled way. Its defining characteristics are:

CharacteristicExplanation
Self-describing natureA database contains not just data, but also a description of itself (the metadata / data dictionary) — table names, field names, data types, and relationships.
Insulation between programs and data (Data Abstraction)The physical storage structure can be changed without changing the application programs that use the data.
Support for multiple views of dataDifferent users can see different "views" or subsets of the same database suited to their needs, without duplicating the underlying data.
Data sharing and multi-user accessMany users/programs can access the same data concurrently, with the DBMS controlling conflicts (concurrency control).
Control of data redundancyRelated data is stored once in a shared, integrated structure instead of many separate copies.
Data integrity enforcementBuilt-in rules (constraints) ensure data is accurate and valid, e.g. a foreign key must match an existing record.
Data securityAccess is granted through authentication and permissions — different users can be given different rights (read-only, edit, admin).
Backup and recoveryThe DBMS provides mechanisms to recover the database to a consistent state after a crash or failure.
Query and reporting facilityUsers can retrieve exactly the data they need using a query language (typically SQL) without writing a full program.
Example: In a Bank DBMS, the same customer record is used by the Loans department, the Savings department, and the ATM system (data sharing); if a customer's address is wrong, it is fixed once and reflected everywhere (integrity/no redundancy); and a teller can view balances but not change interest rates, while an admin can do both (security).

3. Data Processing System

"Data processing" is the conversion of raw data into meaningful information. It is useful to compare how this was done before DBMS (traditional file processing) versus with a DBMS.

3.1 Traditional File Processing System

  • Each application has its own private data file(s), designed only for that application.
  • Programs and data are tightly coupled — a change in file structure forces a change in the program (no data independence).
  • Leads to data redundancy, inconsistency, and difficulty in sharing data across departments.

3.2 Database Processing System (DBMS-based)

  • All data is stored in a single, integrated, centrally-controlled database.
  • Applications interact with the data through the DBMS, not directly with the physical files.
  • Supports concurrent access, integrity checks, security, and recovery as built-in services.
Fig 2: Users and application programs never touch the raw stored data directly — every request is processed through the DBMS, which consults the data dictionary (metadata) and enforces rules before reading/writing the actual database.

4. Components of a DBMS Package

A commercial DBMS (e.g. MySQL, Oracle, PostgreSQL, SQL Server) is not a single program — it is a package made up of several cooperating components:

Fig 3: Typical components that together form a DBMS package
  • DDL (Data Definition Language) compiler — processes schema definitions (creating tables, defining data types, e.g. CREATE TABLE) and stores them as metadata.
  • DML (Data Manipulation Language) processor — handles insertion, updating, deletion of data (e.g. INSERT, UPDATE, DELETE).
  • Query processor — interprets a query (e.g. an SQL SELECT), chooses an efficient execution plan, and retrieves the result.
  • Data manager (storage manager) — the software that actually reads and writes data blocks to and from physical storage.
  • Transaction manager — ensures every transaction follows the ACID properties (Atomicity, Consistency, Isolation, Durability) — e.g. a bank transfer either completes fully or not at all.
  • Concurrency control manager — prevents problems when two users try to update the same record at the same time.
  • Data dictionary / system catalogue — the "metadata" store describing every table, field, constraint, and relationship in the database.
  • Backup and recovery manager — maintains logs and backups so the database can be restored after a system failure.
  • Security manager — authenticates users and enforces access permissions.

5. Database Administration

The Database Administrator (DBA) is the person (or team) responsible for the overall control and management of the database. Database administration is the set of functions this role performs.

5.1 Key Functions of a DBA

  • Schema definition — creates the original database schema by defining tables, fields, data types, and relationships (using DDL).
  • Storage structure and access method definition — decides how data is physically stored and indexed for efficient retrieval.
  • Granting authorisation for data access — decides which users/roles can read, insert, update, or delete which parts of the data.
  • Routine maintenance — periodic backups, monitoring disk space, applying patches/updates.
  • Ensuring data integrity and security — enforcing constraints, setting up firewalls/passwords, auditing access.
  • Performance monitoring and tuning — watching query speed and optimising indexes or configurations.
  • Backup and recovery planning — preparing for disk crashes, power failures, or accidental deletions so data can be restored.
  • Liaison with users — resolving user problems, training staff on proper data-entry practices.
Example: In a university ERP, the DBA decides that the "Registrar" role can edit student marks, the "Faculty" role can only enter marks for their own subject, and "Students" can only view (not edit) their own marks — and takes a nightly backup of the whole database in case of failure.

6. Entity–Relationship (E-R) Model — Conceptual Design

The Entity–Relationship model is a high-level conceptual data model used to describe the structure of a database in a way that is easy for both designers and non-technical stakeholders to understand, before it is converted into actual database tables.

6.1 Basic Building Blocks

TermMeaningExample
EntityA real-world object or concept about which data is stored.Student, Course, Teacher
Entity SetA collection of similar entities.All Students in the college
AttributeA property or characteristic that describes an entity.Student → Roll_No, Name, DOB
Key AttributeAn attribute that uniquely identifies each entity (primary key).Roll_No for Student
RelationshipAn association between two or more entities.Student "enrolls in" Course
CardinalityDescribes how many instances of one entity relate to instances of another.One Teacher teaches Many Courses (1:M)

6.2 E-R Diagram Notation

Fig 4: Standard E-R notation — Rectangle = Entity, Diamond = Relationship, Oval = Attribute, Underlined Oval = Key/Primary attribute

6.3 Worked Example: "Student enrolls in Course"

Consider a simple college scenario: Students enroll in Courses, and each enrolment has a Grade. Each Student has a Roll_No (key), Name, and Email. Each Course has a Course_ID (key), Title, and Credits.

Fig 5: Conceptual E-R diagram — STUDENT and COURSE entities connected by the many-to-many ENROLLS-IN relationship, which itself carries the attribute "Grade"

6.4 Types of Attributes

  • Simple attribute — cannot be divided further, e.g. Roll_No.
  • Composite attribute — can be split into sub-parts, e.g. Name → First_Name + Last_Name.
  • Single-valued attribute — has only one value, e.g. DOB.
  • Multi-valued attribute — can have several values, e.g. a Student can have multiple Phone_Numbers.
  • Derived attribute — calculated from another attribute, e.g. Age derived from DOB.

6.5 Types of Relationships (Cardinality)

TypeMeaningExample
One-to-One (1:1)One entity instance relates to exactly one instance of another.One Employee has one Employee_ID card.
One-to-Many (1:M)One entity instance relates to many instances of another.One Department has many Employees.
Many-to-Many (M:N)Many instances of one entity relate to many instances of another.Students enroll in many Courses; Courses have many Students.

6.6 Why the Conceptual E-R Model Matters

The E-R diagram is drawn before any table is created in the DBMS. It lets designers validate the business requirements with users first (in plain, visual terms), and is then systematically converted into actual relational tables — a process called mapping the E-R model to a relational schema (e.g. the ENROLLS-IN relationship above would become its own "Enrollment" table containing Roll_No, Course_ID, and Grade as foreign/primary keys).

Quick Revision Summary

  • Database approach objectives: less redundancy, no inconsistency, data sharing, enforced standards & security, integrity, balanced views, data independence.
  • DBMS characteristics: self-describing (metadata), program-data insulation, multiple views, sharing, controlled redundancy, integrity, security, backup/recovery, query facility.
  • Data processing: file-based (siloed, redundant) vs database-based (centralised, DBMS-mediated).
  • DBMS components: DDL compiler, DML processor, query processor, data manager, transaction manager, concurrency control, data dictionary, backup/recovery, security manager.
  • DBA functions: schema design, storage/access definition, authorisation, integrity/security, backup/recovery, performance tuning, user support.
  • E-R model: Entities (rectangles) + Attributes (ovals, key underlined) + Relationships (diamonds), with cardinality (1:1, 1:M, M:N) — used for conceptual design before building actual tables.
